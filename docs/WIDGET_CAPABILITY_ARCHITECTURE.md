# Widget & Engine Architecture — Capability & Security Model

**Status:** Design (pre-implementation)
**Scope:** How overlay widgets connect to the VortiDeck engine, the capability/permission model that makes third-party widgets safe, and the path to "widgets as first-class engine participants."
**Companion:** `WIDGET_CAPABILITY_DIALOG_PLAN.md` (implementation plan)

---

## 1. The engine core is a typed EventBus spine

VortiDeck's core (`vortideck-core`) is well-factored around a single **`EventBus`** carrying one tagged enum (`EventPayload`) with these categories:

| Category | Meaning |
|---|---|
| `Stream` | Platform events: Follow, Subscription, Raid, Bits, ChatMessage, StreamOnline/Offline, ViewerCountUpdated |
| `Flow` | Flow lifecycle: FlowStarted, NodeStarted/Completed/Progress/Failed, FlowCompleted/Failed/Cancelled, ExecutionStateChanged/History, WebhookResponseReady |
| `System` | VolumeChanged, SystemInfoRetrieved |
| `Webhook` | WebhookReceived |
| `Relay` | Mobile commands/connection status (StatusChanged, CommandReceived, MobileConnected/Disconnected) |
| `Session` | Session lifecycle (Created/Updated/Deleted/Activated/Deactivated) |
| `Auth` | TokenSaved/TokenCleared |
| `Generic { source, eventType, payload }` | Schemaless escape hatch — custom webhooks, Ko‑fi, new integrations, plugins, **flow-emitted data** |

Every producer (streaming WS, flow executor, relay, session manager) publishes here; every consumer subscribes. **This is the universal data mechanism** — typed variants for known shapes, `Generic` for anything else. The architecture is sound.

---

## 2. What widgets connect to TODAY (the bridge is a narrow funnel)

The overlay bridge (`main.rs` EventBus→Overlay task) forwards to widget iframes:

| Category | Reaches widgets? | Notes |
|---|---|---|
| `Stream` | ✅ all variants | The main surface — chat + alert-style widgets |
| `Generic` | ✅ | Custom webhooks, Ko‑fi, plugins |
| `Flow` | ⚠️ only `FlowCompleted` | All other flow events are dropped (`_ => {}`) |
| `Session` | ⚠️ only `clearChat` | On activate/deactivate |
| `System` / `Webhook` / `Relay` / `Auth` | ❌ | Dropped |
| Macros | ❌ | Not on the EventBus at all |

Today this is "safe" **only because every widget is builtin/trusted.** The risk appears the moment third-party/marketplace widgets exist.

---

## 3. The unifying idea: widgets ARE plugins

VortiDeck already has:
- a **permission system** — `PermissionChecker` + `PluginPermission` enum (`Flows`, `Storage`, `Network`, …) with grant/enforce/revoke (`plugins/permissions.rs`, `plugins/bundle.rs`).
- a **plugin SDK** — `packages/plugin-sdk` (host-function API for flow plugins, generated by `pdk-gen`).

The clean end-state: **a widget is just a plugin with a visual surface.** It declares capabilities, the user grants them at install, the checker enforces. Widgets inherit permissions + SDK + UI-panel capability for free instead of today's ad-hoc postMessage bridge.

## 3.5 Package & Contribution Model (the plugin taxonomy)

**Honest framing: this is a *generalization* of what already exists, not a new invention.**

**Today** (`bundle.rs` → `PluginManifest`): one manifest per package; `runtime` (`Wasm`|`Service`) = one logic entry; optional `web` (extension.js/styles/assets) = one web/UI layer. So a package **already** carries "code + web UI" together. Permissions are package-level. Bundled as `.vdext` (wasm + manifest + `web/` + signature). `PluginWatcher` reloads the folder.

**The evolution:** replace the fixed `runtime` + `web` fields with a typed **`contributions` list**, and add **`widget`** (plus `macro`, `ui-panel`) as contribution types. Same package / manifest / permissions / bundle / watcher — just a richer "what does this package contribute" declaration:

```jsonc
{
  "id": "donation-alert",
  "name": "Donation Alert",
  "version": "1.0.0",
  "permissions": ["Network", "Flows"],
  "contributions": [
    { "type": "flow-node",  "node": { … } },
    { "type": "widget",     "capabilities": { … }, "content": "alert.html" },
    { "type": "ui-panel",   "panel": "config.html" }
  ]
}
```

**Contribution types:** `flow-node`, `widget`, `ui-panel`, `macro`, `code` (wasm/service logic). A package may declare N contributions of any mix (single-widget packages are just the N=1 case).

| | Reused (not new) | Genuinely new |
|---|---|---|
| Package, manifest, permissions, `.vdext`, watcher, SDK | ✅ | |
| Typed `contributions` list | | ✅ (generalizes `runtime`+`web` → N typed entries) |
| `widget` contribution type + capability/subscribe/render | | ✅ |
| Per-contribution capability granularity in the dialog | | ✅ |

**Mapping to today (backward compatible):** `runtime: Wasm` → a `code` contribution; `web` → a `ui-panel`/`widget` contribution. `contributions` is optional, so legacy manifests with `runtime`/`web` still load; the dialog reviews the package (all contributions) at one install.

> Minimal alternative: widgets could be shoehorned into the existing `web` field + a capabilities flag without a contributions list. The list is preferred for clarity/extensibility (macros, ui-panels, multiple widgets), but it's a small evolution of `runtime`+`web`, not a rewrite.

## 4. Capability & permission model

> **Terminology — "capability" vs "permission": same idea, two granularities.**
> - A **permission** is the *coarse, host-defined category* from the existing flow-plugin system (`PluginPermission::{Network, Flows, Storage, Dom, Css, FileSystem}`) — "what *kind* of thing."
> - A **capability** is the *specific, instance-level grant* — `subscribe:["follow"]`, `triggerFlow:"flow_42"`, `network:whitelist:[…]`, `openUi` — "exactly *what*."
>
> A capability is a more precise permission (`network:whitelist` implies `Network`). **There is exactly one permission system** — `PermissionChecker` + the `PluginPermission` enum. We do **not** build a second one. We **extend `PluginPermission`** with widget-capability variants (`SubscribeEvent(String)`, `TriggerAction(String)`, `OpenUi`; `Network` already exists) and **reuse the same `PermissionChecker`**, keyed by widget/package id. **"Capability" is only the user-facing word** for these permissions in the manifest/dialog — internally it is still `PluginPermission` + `PermissionChecker`, one system.

A widget package ships a **manifest**:

```jsonc
{
  "id": "follower-goal",
  "name": "Follower Goal",
  "creator": "@streamerdevs",
  "trust": "verified",                 // "builtin" | "verified" | "community"
  "content": "<iframe HTML/CSS/JS>",
  "capabilities": {
    "subscribe": ["follow", "raid"],            // events it wants to receive
    "actions":  ["triggerFlow:flow_42"],        // outbound calls it wants to make
    "ui": true,                                 // may open a settings/interaction panel
    "network": "none"                           // "none" | "whitelist" | "full"
  },
  "permissions": ["Flows"]                      // maps to PluginPermission
}
```

- **`subscribe`** = inbound data scope (least privilege: the widget only receives these events).
- **`actions`** = outbound scope (only these calls permitted; checked by `PermissionChecker`).
- **`ui`** = may open a panel (like flow plugins).
- **`network`** = drives CSP `connect-src` (see §6).
- **`permissions`** = the existing `PluginPermission` set.

User approves at install; stored via `PermissionChecker.grant_permissions(widget_id, …)`; revocable anytime.

## 5. Four-layer defense (defense in depth)

```
Layer 1 — SANDBOX        iframe sandbox="allow-scripts"  (NO allow-same-origin for untrusted)
Layer 2 — CSP            connect-src driven by the `network` capability
Layer 3 — CAPABILITIES   inbound events filtered + redacted; outbound calls gated
Layer 4 — CHECKER        PermissionChecker.has_permission() before every action
```

| Layer | Stops |
|---|---|
| Sandbox (no `allow-same-origin`) | Reading `window.parent`, siblings, cookies, `localStorage`. Opaque origin; postMessage still works. |
| CSP `connect-src` | `fetch`/`WebSocket`/XHR exfiltration to external servers. |
| Capabilities | Receiving un-granted events; reading redacted fields. |
| Checker | Executing un-granted outbound actions. |

---

## 6. Sandbox vs CSP — they are orthogonal

- **Sandbox** controls **isolation**: what the widget can read/touch inside the app.
- **CSP** controls **network**: what the widget can send/receive over the wire.

A widget receives data via `postMessage` from the bridge — it doesn't need parent access to leak it. It can `fetch()` that data to `evil.com`. Sandbox (even without `allow-same-origin`) does **not** block that; CSP `connect-src` does. **Both are required.**

**Permissions drive the CSP** — the `network` capability selects the policy:

| `network` capability | Resulting CSP |
|---|---|
| `none` (default) | `connect-src 'none'` |
| `whitelist` | `connect-src https://api.example.com` (+ manifest URLs) |
| `full` | relaxed / unrestricted (high-risk; trusted only) |

> Note: today's widget iframes use `sandbox="allow-scripts allow-same-origin"`, so they **can** reach the parent — acceptable because they're trusted builtins. Untrusted/marketplace widgets drop `allow-same-origin` and gain a CSP.

## 6.5 Threat model & where authority lives

**Core principle: capabilities are granted by the user (the grant record), not claimed by the package.** A widget cannot give itself capabilities by editing its files, its manifest, or its location — authority flows from the user-approved grant record stored in the (tamper-evident) DB.

**The four threats and how each is handled:**

1. **Malicious marketplace widget (no local access)** — the *primary* threat. The widget iframe is sandboxed (no `allow-same-origin`) and cannot reach `invoke()`; flow/service plugins only have the SDK host API. Nothing untrusted can call `install_widget`/`revoke_widget`. Capabilities arrive only via the dialog → `install_widget` grants exactly the **approved** set. *Safe by the trust boundary.*

2. **Signature/content tampering of an installed package** — the grant record pins `content-hash = X` (+ trust level) at install. On load the hash is re-verified, and that check is **grant-bound** (stored in the MAC-protected grant record), *independent of whether the signature file still exists*. Modified content → hash mismatch → refused / dropped to zero capabilities. Stripping the signature does **not** bypass the hash check.

3. **"Downgrade to dev" attack** (strip signature / move to dev folder to escape checks) — does **not** work:
   - Grant record exists → widget is pinned as *installed* (hash-checked) regardless of folder. Stripping the signature changes the package, not the grant.
   - Grant record deleted too → widget has **zero granted capabilities** until re-approved; re-approval shows it as **unverified/community** (signature gone) — the scary dialog, no silent escalation.
   - The dev-folder exemption is a **config property** (`in dev folder` AND `dev mode on` AND `no installed grant record`), not a package self-label — a package can't flip it.

4. **Privileged local attacker / admin malware** — *out of scope* (fundamental, like DRM). Such an attacker could edit the DB, delete grants, flip dev mode, extract keys. Tamper-evidence (content hash + grant MAC + verify-on-load) raises the bar and forces any escalation to surface as an *unverified re-install*, but cannot fully stop a determined admin. Accepted limitation of desktop software.

**Authority summary:** the grant record (`widget_id → approved capabilities + content-hash + trust`, MAC-protected) is the single authority. Package files are *content*; the folder + dev-mode are *config*; neither grants capabilities. Only the user's dialog approval does — recorded tamper-evidently.

## 7. Universal data flow — flows can emit, the bus carries it

The `EventBus` is the single universal channel between all engine parts:

```
streaming ─┐
flows ─────┼──► EventBus ──┬──► overlay bridge ──► widgets (capability-filtered)
relay ─────┤               ├──► IPC bridge ──► editor UI (trusted)
macros* ───┘               └──► other flows / macros / persistence
```

**Flows as producers:** add an **"Emit Event"** flow node that publishes onto the bus — as a `Generic { source: "flow:<id>", eventType, payload }` or a typed event. This lets a flow (e.g., one that processes donations) feed data that widgets/other flows/UI consume. It turns flows from pure sinks into producers and **closes the engine loop.** It makes complete sense.

**Why this is the right universal mechanism:** typed variants for known shapes (compile-checked end-to-end), `Generic` for anything arbitrary (no schema needed), and exactly one filter point for the untrusted boundary (the overlay bridge). Adding a new data source = new events on the bus; nothing else rewrites.

---

## 8. Subscription vs broadcast

- **Current (broadcast):** `querySelectorAll('iframe').forEach(postMessage(event))` — every widget receives every stream/generic/flowCompleted event; each ignores what it doesn't want.
- **Subscription (target):** the bridge filters by each widget's granted `subscribe` list **before** delivering — a widget never receives events it didn't ask for. Least privilege, less traffic, smaller exfiltration surface.

`subscribe` is the **request**; the permission grant is the **approval**. A widget can request `chatMessage` but only receive it if granted.

---

## 9. Two-way (widget → engine), gated

Widgets may call out (trigger a flow, fire a webhook, run a macro, open UI). Every outbound message is checked by `PermissionChecker.has_permission(widget_id, action)` before execution.

- **Allowed with permission:** subscribe to specific events, trigger *whitelisted* flows, open a UI panel, read own config, whitelisted network.
- **Denied:** arbitrary network, trigger *any* flow, raw PII payloads, keyboard-sim macros (keylog risk), access other widgets' data.

This unlocks interactive widgets (polls, mini-games, buttons) without giving them a blank check.

---

## 10. Macros on the bus — lifecycle only

**Pros:** cohesion (flows/widgets/relay react to macros), observability, chaining (macro done → flow), "macro status" widget, mobile-triggered-macro reflection, audit log.
**Cons:** noise (rapid keybinds); privacy (keystroke details — a macro may type a password).

**Decision:** emit **lifecycle only** — `MacroStarted`/`MacroCompleted` with macro id + name, **never inputs.** Optionally throttled or opt-in. High cohesion value, near-zero risk.

Today the execution service (`services/execution`) does not emit to the bus at all — it's a parallel island. Putting lifecycle events on the bus makes the engine cohesive.

---

## 11. SDK / contract

There **is** a plugin SDK (`packages/plugin-sdk`) — but it covers **flow plugins** (the host-function API). It does **not** cover overlay widgets, which use the ad-hoc `vortideck-stream-event` / `UPDATE_DATA` / `UPDATE_VARS` postMessage bridge (undocumented).

**Contract = extend the SDK to cover widgets:** typed event types, `widget.subscribe(...)`, `widget.trigger(...)`, theming vars (`--c-*`), capability declarations, manifest schema. This is the creator-facing surface the marketplace needs.

---

## 12. UX flow (what the user sees)

1. **Add widget** → capability dialog (modal): name, creator, trust badge, install count, requested capabilities in plain language, Allow/Cancel. (Mirrors flow-plugin install.)
2. **Editor** → widget renders on canvas like any builtin, with a subtle "community/sandboxed" badge; right-click → Permissions.
3. **Manage permissions** → global "Extensions/Widgets" page or per-widget panel; toggle/revoke grants instantly.
4. **Runtime prompts** → if a widget attempts an un-granted capability, one-time prompt (Allow once / Always / Deny) — the browser-permission pattern.
5. **Editor vs OBS** → all permission UI is editor-only; in OBS, enforcement is invisible (bridge just doesn't deliver/gate).
6. **Graceful failure** → sandbox/CSP blocks are silent; widget degrades or shows its own "needs permission" state. No scary errors.

---

## 13. Recommendations (ordered)

The security model is the **prerequisite**, not an add-on. Sequence:

1. **Route widgets through `PermissionChecker`** (widgets = plugins; manifest declares capabilities; grant at install).
2. **Per-widget sandbox + CSP** — drop `allow-same-origin` for untrusted; CSP from the `network` capability.
3. **Capability-filtered bridge** — subscribe + redact inbound; gate outbound (two-way).
4. **Capability dialog + management UI** (see plan doc).
5. **Widen the bridge** (forward Flow/System/Webhook/Relay) **behind capabilities.**
6. **Macros emit lifecycle** on the bus.
7. **Flow "Emit Event" node** → bus (closes the loop).
8. **Extend the SDK** to cover the widget surface (the contract).

Do **not** collapse the two `EventBus` subscribers into an auto-forward-all pipe — they serve different trust domains (IPC bridge → trusted editor; overlay bridge → untrusted widgets). Keep them separate; make the overlay one capability-aware.

---

## Bottom line

The core engine is solid — a typed `EventBus` spine with a `Generic` escape hatch is the right design. The weakness is concentrated in the **widget↔engine seam**: today it's a narrow, one-way, broadcast-only funnel that hides most of the engine from widgets and has no security boundary for third-party code. Fixing that seam runs through the **permission system that already exists** (`PermissionChecker` / `PluginPermission`): treat widgets as plugins, declare capabilities, sandbox + CSP untrusted ones, and filter everything through grants. That turns "widgets can show chat" into "widgets are first-class, safe engine participants" — the marketplace promise.
